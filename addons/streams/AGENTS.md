# streams — инструкции для агентов

Модуль переработки системы сообщений Odoo 19 (потоки, каналы записей,
уведомления, гостевой доступ, виртуальный чаттер партнёра). Общие правила
репозитория — в корневом `AGENTS.md`; здесь только специфика модуля.

## Документация (`docs/`, на английском)

| Файл | Что это | Когда править |
|---|---|---|
| `docs/concept.md` | Как модуль устроен **сейчас**: терминология, архитектура, правила потоков, инварианты, принятые решения | При любом изменении поведения — в том же коммите |
| `docs/user-guide.md` | Руководство сотрудника и раздел для гостя | При изменении UI или пользовательских сценариев |
| `docs/admin-guide.md` | Установка, настройки, что меняется в стандартном Odoo, безопасность, эксплуатация, тесты, RPC/bus-контракт | При изменении настроек, прав, роутов, кронов, контракта |
| `docs/roadmap.md` | **Только** несделанное: приоритеты P0–P3, непроверенное, решения за владельцем продукта | Закрыл пункт — удали его и перенеси описание поведения в concept; нашёл дефект — добавь |
| `docs/history/` | Исходное ТЗ (`history/roadmap.md`, русский, с историей фаз 1–9.7) и дизайн-контракты фаз. Не редактируются | Никогда; только читать за контекстом решений |

Правила:

- Перед задачей по модулю прочитай `concept.md` целиком (терминология §2,
  архитектура §3, инварианты §12 обязательны к соблюдению) и релевантные
  пункты `roadmap.md`.
- Источник правды — код. Документация описывает код, а не намерения; если
  они расходятся, сначала решить, что менять, потом синхронизировать оба.
- Отступление от концепции по решению пользователя фиксируется в
  `concept.md` §13 «Decisions» с датой.
- Дизайн новой крупной работы — отдельным документом `docs/design-<тема>.md`;
  после реализации его переносят в `docs/history/`.
- В корне модуля файлов документации не заводить (кроме этого AGENTS.md
  и CLAUDE.md).

## Ключевые инварианты модуля

- Чаттер записи и канал записи — две проекции одного набора `mail.message`
  (m2m `stream_channel_ids`), не два хранилища.
- Подписка (followers) только явная; followers — только внутренние
  пользователи; участники канала ⇄ followers синхронизированы двусторонне
  (guard-контекст `streams_sync`).
- Внутренние пользователи не получают email из записей. Никогда.
- `change`-сообщения не влияют на unread и сортировку каналов, не создают
  канал и не рассылаются по шине.
- Bus-рассылка проекций — только участникам с правом чтения записи-источника;
  лента партнёра и лента Changes перепроверяют права при каждом чтении.
- Гость видит только comment и message; уведомления (`mail.notify`) никогда
  не попадают в чаттер, каналы и email.

## Тесты

Все сценарии — в `tests/` (python) и `static/tests/` (Hoot, туры). Любая
правка модуля прогоняется `run_odoo_tests(modules="streams")`; браузерные
тесты в контейнере пропускаются — гонять с хоста (рецепт в
`admin-guide.md` §7 и `tests/test_js.py`). Ломать существующие сценарии
нельзя без явного решения архитектора, зафиксированного в `concept.md`.
