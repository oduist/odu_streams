# Roadmap: Переработка системы сообщений Odoo 15 (модуль streams)

Живой документ проекта. Исходник — ТЗ из gist
(https://gist.github.com/litnimax/260455d6b465de5bd4939178476ede60), сюда
вносятся правки по ходу работы: реализованные части переносятся в раздел
«Сделано» в конце файла, отступления от исходного ТЗ фиксируются там же,
проверки, отложенные «на потом», — в разделе «To check / to do».

**Версия:** 1.2 (обновлено 2026-08-18)
**Целевая платформа:** **Odoo 19.0** (решение пользователя 2026-08-18; фазы
1–4 реализованы и приняты на Odoo 15, порт на 19 — фаза 5,
`docs/design-phase5.md`). Следующий этап после порта — мобильный клиент:
модуль `streams_mobile` (токен-аутентификация, API `/streams/mobile/v1/`,
пуши FCM) и приложение на Flutter.
**Охват моделей:** все наследники `mail.thread` без исключений.

---

## 1. Цель

Текущий чаттер Odoo сваливает в одну ленту четыре разных по смыслу вида контента (переписка, заметки, аудит изменений, системные события), а механизм подписчиков (followers) работает для всех них одинаково и по умолчанию утекает наружу — внешние контрагенты автоматически подписываются на записи и получают письма о внутренних событиях.

Задача — разделить чаттер на потоки с независимой семантикой доставки, полностью убрать автоматическую подписку и автоматическую внешнюю рассылку, вынести обсуждение записей в Discuss в виде каналов, ввести отдельный приоритетный канал уведомлений и контролируемый гостевой доступ клиентов по одноразовой ссылке.

---

## 2. Терминология

Терминология переопределяется относительно стандартной Odoo. Ниже — единственно корректное употребление в рамках проекта.

| Термин | Подтип | Смысл | Приватность |
|---|---|---|---|
| **Заметка** | `note` | Внутренняя запись «для себя и коллег» | Полностью приватная. Единственный подтип, недоступный приглашённому клиенту |
| **Комментарий** | `comment` | Внутреннее общение сотрудников по записи | Внутренний по назначению, но **виден приглашённому в канал клиенту** |
| **Сообщение** | `message` | Внешняя коммуникация: письма от клиентов и клиентам | Внешняя |
| **Изменение** | `change` | Изменение поля с `tracking=True` | Внутреннее |
| **Активность** | `activity` | Синтетическое сообщение о событиях `mail.activity` | Внутреннее, клиенту не видно |
| **Уведомление** | — (отдельная модель) | Приоритетное адресное уведомление с всплывающим окном | Внутреннее |

**Важно:** то, что в ранних обсуждениях называлось «внутренним сообщением», здесь и далее называется **комментарием**. «Сообщение» — исключительно внешняя коммуникация.

## 3. Общая архитектура

Три вида каналов:

1. **Канал записи** — `mail.channel`, привязанный к конкретной записи (`res_model` + `res_id`). Групповое обсуждение записи. Создаётся лениво. Участники = followers записи.
2. **Личный канал Changes** — по одному на пользователя. Лента изменений полей, на которые пользователь явно подписался. Группируется по записям-источникам.
3. **Личный канал Notifications** — по одному на пользователя. Служебный канал приоритетных уведомлений. Отдельная иконка в навбаре.

Чаттер записи и канал записи — **две проекции одного набора `mail.message`**, а не два хранилища. Сообщение пишется один раз и связывается с каналами.

## 4. Модель данных

### 4.1. `mail.message` (расширение)

- Расширить справочник подтипов: `note`, `comment`, `message`, `change`, `activity`.
- Существующий механизм `mail.message.subtype` переиспользуется; добавляются новые записи подтипов.
- Связь сообщения с каналами — many2many (сообщение может принадлежать каналу записи и одновременно личным каналам Changes нескольких пользователей).

### 4.2. `mail.channel` (расширение)

Новые поля:

| Поле | Тип | Назначение |
|---|---|---|
| `channel_kind` | selection | `record` / `changes` / `notifications` |
| `res_model` | char | Модель записи-источника (для `record`) |
| `res_id` | integer | ID записи-источника (для `record`) |
| `owner_user_id` | m2o `res.users` | Владелец личного канала (для `changes` / `notifications`) |
| `company_id` | m2o `res.company` | Наследуется от записи-источника |
| `active` | boolean | Синхронизирован с `active` записи-источника |

Индекс по `(res_model, res_id)`.

### 4.3. `mail.field.subscription` (новая модель)

Персональная подписка на изменения полей конкретной записи.

| Поле | Тип |
|---|---|
| `user_id` | m2o `res.users` |
| `res_model` | char |
| `res_id` | integer |
| `field_ids` | m2m `ir.model.fields` |

Уникальность по `(user_id, res_model, res_id)`. Индекс по `(res_model, res_id)`.

### 4.4. `mail.channel.guest.link` (новая модель)

Гостевой доступ клиента к каналу записи.

| Поле | Тип | Назначение |
|---|---|---|
| `channel_id` | m2o `mail.channel` | |
| `partner_id` | m2o `res.partner` | Конкретный контакт, не компания |
| `token` | char | Секрет ссылки, длинный случайный |
| `history_from` | datetime | С какого момента гость видит историю |
| `session_token` | char | Выдаётся после первого осознанного входа |
| `session_expiry` | datetime | Срок жизни сессии |
| `is_link_consumed` | boolean | Ссылка уже обменяна на сессию |
| `active` | boolean | Отзыв доступа |
| `last_seen` | datetime | Heartbeat присутствия |
| `last_digest_sent` | datetime | Для часового дайджеста |

### 4.5. `mail.notify` и `mail.notify.recipient` (новые модели)

Уведомления **не являются** `mail.message`, не подшиваются в чаттер и не попадают в каналы записей.

`mail.notify`:

| Поле | Тип |
|---|---|
| `author_id` | m2o `res.users` |
| `body` | html/text |
| `attachment_ids` | m2m `ir.attachment` |
| `voice_attachment_id` | m2o `ir.attachment` |
| `transcript` | text |
| `transcript_state` | selection: `none` / `queued` / `done` / `failed` |
| `res_model`, `res_id` | источник (опционально — уведомление может быть без привязки к записи) |
| `is_sticky` | boolean |
| `timeout` | integer, сек, по умолчанию 10 |
| `parent_id` | m2o `mail.notify` — цепочка ответов |

`mail.notify.recipient`:

| Поле | Тип |
|---|---|
| `notify_id` | m2o `mail.notify` |
| `user_id` | m2o `res.users` |
| `read_date` | datetime |
| `popup_shown` | boolean |

## 5. Канал записи

### 5.1. Создание

Канал **не** создаётся вместе с записью и **не** создаётся заранее.

Триггеры создания:

- первый **комментарий** по записи;
- первая **заметка**;
- первое **сообщение** (внешнее письмо, входящее или исходящее);
- первое событие **activity** (создание активности);
- **приглашение внешнего участника** из чаттера записи (пятый триггер,
  решение пользователя 2026-08-18, фаза 4). Кнопка `Invite customer` есть и в
  чаттере, и в шапке канала; из чаттера она работает на записи без канала —
  канал создаётся приглашением. Канал «скрыт» естественным образом: его видят
  только участники, а участники = followers; пригласивший увидит канал, когда
  подпишется (напишет комментарий) или будет подписан автоматически по ответу
  клиента (§9.7).

**Не создают канал:**

- само создание записи (сообщение «Запись создана»);
- изменения полей — сколько угодно изменений не приводят к появлению канала. Они пишутся в чаттер и в личные ленты Changes подписавшихся;
- присоединение участника (follower). Follower может быть добавлен, канал при этом не появляется.

Подписка авторов (правило от 2026-08-18): **автор комментария или внешнего
сообщения подписывается на запись автоматически** — и тот, кто начал
обсуждение, и каждый, кто отвечает. **Автор заметки не подписывается**:
заметка — способ написать в канал, не подписываясь. Внешние контакты не
подписываются никогда; изменения полей и события активностей никого не
подписывают. Ядровое добавление «создателя канала» в участники вырезано —
членство даёт только это правило и явная подписка.

При создании канала к нему **подшивается вся предыдущая история сообщений записи**, включая накопленные изменения (у сообщений проставляется связь с каналом).

### 5.2. Имя канала

Имя канала = `display_name` записи (например, `S00025`). При изменении `display_name` записи (например, черновик счёта получает номер `INV/2026/0001`) канал переименовывается синхронно — по `write` на полях, влияющих на `display_name`.

### 5.3. Участники

Участники канала ≡ `message_follower_ids` записи. Синхронизация **двусторонняя и полная**:

- добавление follower на записи → пользователь добавляется в канал;
- добавление участника в канал → пользователь добавляется в followers записи;
- удаление участника из канала или самостоятельный выход → снятие с followers;
- снятие с followers → удаление из канала.

Followers — **только внутренние пользователи**. Партнёров-контрагентов добавить в подписчики невозможно (см. §10).

При создании канала в него попадают все текущие followers записи.

### 5.4. Права доступа

Канал виден только участникам. Дополнительно — проверка прав на запись-источник: если пользователь потерял доступ к записи (record rules), канал ему не показывается. Мультикомпани: канал наследует `company_id` записи, пользователь без доступа к этой компании канал не видит.

### 5.5. Архивация

Жёсткая сцепка «один к одному» с записью:

- запись архивируется → канал `active = False`, исчезает из списка;
- запись разархивируется → канал разархивируется;
- если в архивированной записи появляется новое сообщение → канал автоматически разархивируется;
- архивированный канал = неработающие гостевые ссылки.

### 5.6. Слияние записей

При merge (партнёры, лиды) каналы сливаются в один: сообщения второго канала переносятся в канал записи-получателя, второй канал архивируется.

### 5.7. Непрочитанное и сортировка

- Счётчик непрочитанных — стандартный.
- Автопометка прочитанным при доскролле до низа.
- **Изменения (`change`) не влияют ни на счётчик непрочитанных, ни на сортировку каналов.** Иначе при импортах и массовых `write` список каналов будет непрерывно перестраиваться, а счётчик у пользователей с выключенным фильтром Changes — «залипать».

## 6. Потоки и фильтры канала

В канале записи присутствуют пять потоков. Фильтры — **клиентская настройка отображения, а не подписка**: данные лежат в канале всегда, пользователь решает, что показывать.

| Поток | Фильтр | Значение по умолчанию |
|---|---|---|
| Комментарии | Comments | вкл |
| Заметки | Notes | вкл |
| Сообщения (внешняя переписка) | Customers | вкл |
| Изменения | Changes | **выкл** |
| Активности | Activities | вкл |

Настройка фильтров — **персистентная, per-channel, per-user**.

---

## 7. Правила уведомления по потокам

| Поток | Кого уведомляем |
|---|---|
| Заметка | Никого, кроме явно упомянутых в теле через `@mention`. Упоминание — единственный триггер |
| Комментарий | Участников канала (счётчик непрочитанных) |
| Сообщение | Клиента — по правилам гостевого доступа (§9). Внутренним — счётчик непрочитанных |
| Изменение | Только запись в личный канал Changes подписавшихся на конкретные поля. Попапов нет |
| Активность | Никаких уведомлений. Уведомления только явные, через Notify |

**Внутренние пользователи не получают email в рамках этой системы вообще.** Никогда. Вся коммуникация — внутри Odoo. (В дальнейшем планируется мобильное приложение.) Системные письма Odoo — сброс пароля, приглашение пользователя, mass mailing — под это правило **не подпадают** и не трогаются; речь только об отправке из записей.

## 8. Изменения полей и личный канал Changes

### 8.1. Подписка на поля

- Подписка **персональная**, на уровне конкретной записи: `(user_id, res_model, res_id, field_ids)`.
- **По умолчанию пользователь не подписан ни на одно поле** — ни на одной записи, включая записи, где он участник канала.
- UI: кнопка **Changes** в чаттере записи. Открывает диалог выбора полей.
- При первом открытии диалога по умолчанию **предлагаются** (отмечены) поля с `tracking=True`. Это только предзаполнение; пользователь снимает и добавляет что хочет, его выбор имеет приоритет и сохраняется.
- Подписаться на поля можно **не будучи участником канала** — это отдельная и намеренная возможность. Обратное тоже верно: участник канала не подписан ни на одно поле, пока явно не выберет.
- Поля, к которым у пользователя нет доступа (`groups="..."` на поле), **не показываются в диалоге вовсе** — подписаться на них нельзя.

### 8.2. Запись изменений

При `write` формируется **одно схлопнутое сообщение** подтипа `change` со списком всех изменённых трекаемых полей (как это делает стандартный tracking) — независимо от количества полей и от того, кто на что подписан.

Это сообщение связывается:

- с **каналом записи** — целиком, со всеми полями, видимо всем участникам при включённом фильтре Changes;
- с **личным каналом Changes** каждого подписавшегося пользователя.

В личной ленте пользователь видит **только те `tracking_value`, на которые он подписан** — фильтрация происходит на рендере, отдельные персональные копии сообщений не создаются. Если из пяти изменённых полей пользователь подписан на два, он видит два.

Автор изменения уведомляется наравне со всеми: если пользователь подписан на поле и сам его изменил, изменение попадает и в его личный Changes. Изменения одинаковы независимо от автора.

### 8.3. Структура личного канала Changes

Личный Changes — это `mail.channel` с `channel_kind = 'changes'`, где:

- элемент списка = **запись-источник** (имя записи, кликабельно — ведёт на запись);
- внутри элемента — лента изменений по этой записи с расшифровкой «поле: было → стало»;
- при появлении новых изменений запись **поднимается наверх** списка;
- **счётчик непрочитанных считается по количеству записей**, а не по количеству изменений;
- прочитанным элемент считается **при простом скролле мимо него** (аналогично Notifications).

### 8.4. Потеря доступа

Если пользователь теряет доступ к записи-источнику, все связанные с ней изменения **скрываются из его ленты Changes ретроактивно** — проверка прав выполняется на чтении, привязка к записи сохраняется.

## 9. Гостевой доступ клиентов

### 9.1. Общий принцип

Приглашение клиента в канал — **редкий, штучный сценарий**, а не режим постоянного общения. Чат создаётся под конкретное обсуждение. Портал Odoo **не используется** — рисуется отдельный публичный контроллер.

### 9.2. Приглашение

Диалог приглашения из канала/чаттера:

- выбор одного или **нескольких контактов** (`res.partner`, конкретные контакты, не компании);
- **у каждого контакта — своя отдельная ссылка**, даже если приглашение выдаётся за один раз;
- поле **«показывать историю с»** — datetime, по умолчанию текущий момент. Можно сдвинуть назад, чтобы открыть клиенту предыдущую переписку;
- галочка **«отправить приглашение на email»** — если у контакта есть адрес. Письмо уходит на email `res.partner`, на языке `partner.lang`;
- **публичная ссылка показывается в интерфейсе** — её можно скопировать и передать клиенту вручную (например, через мессенджер, если email отсутствует);
- **предупреждение в диалоге**: приглашённый контакт увидит всю переписку в комментариях и сообщениях начиная с указанного момента.

### 9.3. Механика доступа

- Ссылка **одноразовая**: первый **осознанный** вход (POST по кнопке «Войти в чат», не GET — чтобы ссылку не сжигали корпоративные антифишинг-сканеры почты, автоматически прокликивающие ссылки) обменивает токен на долгоживущий cookie-сессию. После обмена ссылка гасится.
- Срок жизни сессии — **настройка продукта, по умолчанию одна неделя**.
- Сессия **продлевается** при каждом заходе, открытии страницы и отправке сообщения.
- Аутентификации как таковой нет. Личность определяется тем, под какой контакт была сгенерирована ссылка: все сообщения гостя подшиваются в чаттер и канал как сообщения от этого конкретного контакта.
- **Восстановления доступа нет.** Протухшая или потерянная ссылка не возобновляется: клиент запрашивает доступ заново обычной почтой либо продолжает общение по email. Это осознанное решение — так утёкшая ссылка гарантированно перестаёт работать.
- Отзыв доступа: контакт удаляется из чата в любой момент, после чего он не получает и не видит ничего.
- Архивация канала = ссылка перестаёт работать.

### 9.4. Что видит клиент

Видит:

- **комментарии** внутренних пользователей;
- **сообщения** (внешнюю переписку, включая свои);
- вложения из комментариев и сообщений;
- **список участников канала** — ФИО сотрудников как есть, без подмены на название компании;
- историю начиная с `history_from`.

Не видит:

- **заметки** (`note`) — полностью скрыты;
- **изменения** (`change`);
- **активности** (`activity`).

Может:

- писать сообщения;
- прикладывать файлы;
- ставить реакции (стандартные);
- **редактировать своё сообщение в течение 2 минут** после отправки;
- **удалять своё сообщение в течение 2 минут** после отправки. По истечении — нет.

Удаление чужих сообщений и удаление за пределами двухминутного окна доступно только сотрудникам.

### 9.5. Страница гостя

- Отдельный публичный контроллер, рендерящий ленту канала с учётом фильтрации по §9.4.
- **AJAX-поллинг раз в 10 секунд** для обновления ленты. Longpolling-шина Odoo не используется — в 15-й версии это неоправданная возня с `mail.guest` и bus-каналами.
- Пока вкладка открыта — heartbeat, гость считается присутствующим. Потеря связи со вкладкой = гость отсутствует.

### 9.6. Часовой дайджест

Крон **раз в час**:

1. находит каналы, где есть активные гостевые ссылки;
2. отбирает тех гостей, кто **отсутствовал** (нет heartbeat) и для кого за истекший час появились новые сообщения/комментарии;
3. отправляет **короткое письмо-дайджест без содержания переписки** — только факт наличия новых сообщений и ссылка;
4. **вместе с дайджестом выдаётся новая ссылка**: старая инвалидируется, новая сохраняет прежние свойства доступа (в частности, `history_from`).

Дайджест уходит целиком за час, даже если гость был онлайн в начале часа и отключился.

Отправка писем гостю — **единственный** случай исходящей почты в этой системе, помимо явной отправки письма клиенту оператором.

### 9.7. Ответ гостя по email

Приглашение и дайджест уходят с фиксированным `thread_id`, поэтому ответ клиента обычной почтой корректно идентифицируется и подшивается в запись и канал как сообщение от этого контакта — стандартным механизмом.

## 10. Отключение стандартного поведения

Требуется вырезать, а не «настроить»:

1. **Автоподписку целиком** (`_message_auto_subscribe` и производные). Никаких автоматических followers — ни партнёров, ни ответственных, ни внутренних пользователей. Подписка только явная: либо пользователь подписывается сам, либо его подписывает другой сотрудник.
2. **Автоматическую рассылку followers-партнёрам** при событиях записи.
3. **Возможность добавить партнёра-контрагента в followers.** В виджете выбора подписчиков список фильтруется так, чтобы отображались **только контакты внутренних пользователей**. Партнёр-неюзер не показывается и не может быть добавлен.

Внешний контакт получает письмо **только** тогда, когда оператор явно отправляет ему письмо (кнопка Send Message) либо в рамках гостевого дайджеста (§9.6).

## 12. Уведомления (Notifications)

### 12.1. Общее

Уведомления — отдельная приоритетная сущность. **Не** попадают в чаттер, **не** попадают в каналы записей, **не** дублируются на email. Только in-app.

### 12.2. Отправка

Инициировать можно:

- из чаттера записи (кнопка Notify) — уведомление получает ссылку на запись-источник;
- из канала записи;
- из самого канала Notifications — без привязки к записи.

Форма отправки:

- текст;
- **несколько получателей** — любые внутренние пользователи, без ограничений по ролям;
- вложения (файлы);
- **голосовое сообщение** — запись прямо в виджете;
- галочка **sticky**;
- поле **timeout**, по умолчанию 10 секунд — отображается **только если sticky выключен**. При включении sticky поле скрывается, вместо него подсказка: попап висит до тех пор, пока пользователь его не закроет.

Настройки попапа общие для всех получателей одной отправки.

### 12.3. Голосовые сообщения и транскрипция

- Запись голоса доступна **только в виджете уведомлений** (не в чаттере, не в канале записи, не у гостя).
- Аудио хранится как `ir.attachment`.
- При наличии ключа OpenAI в **системных параметрах** — транскрипция **фоновой очередью**: сообщение отправляется сразу, текст доезжает через несколько секунд и размещается **под плеером** в теле уведомления.
- Ключа нет или транскрипция не удалась — просто аудио без текста.
- Для уведомлений с голосовым сообщением **sticky форсируется** — иначе попап может закрыться раньше, чем закончится запись.

### 12.4. Попапы у получателя

- Несколько попапов одновременно: не-sticky показываются поверх и исчезают сами по таймауту; sticky складываются в **стек** с возможностью переключаться между ними и закрывать по одному.
- **Звук — на все уведомления**, не только sticky.
- Получатель офлайн: попапы **показываются при следующем логине**, накопившиеся — стеком.

### 12.5. Канал Notifications

Личный канал с двумя подразделами:

- **Полученные**;
- **Отправленные** — со статусом прочтения по каждому получателю, **с временем прочтения** («прочитано в 14:32»).

Прочитанность: уведомление считается прочитанным, когда пользователь **проскроллил его на экране** в канале Notifications. Счётчик обнуляется соответственно.

### 12.6. Ответы

- На уведомление можно ответить; ответ уходит **только автору исходного** уведомления.
- Ответ по умолчанию наследует настройки попапа исходного уведомления (sticky/timeout), но отвечающий **может их переопределить**.
- Цепочка ответов **не ограничена одним хопом** — обмен уведомлениями допустим, в том числе для передачи файлов.

## 13. Активности

- Каждое событие `mail.activity` порождает синтетическое сообщение подтипа `activity` в чаттере и канале записи: **создание, изменение (перенос даты, смена ответственного), отмена, закрытие** — с описанием.
- **Автор** синтетического сообщения — пользователь, выполнивший действие. Если активность закрылась автоматически (крон, серверное действие) — автор **OdooBot**.
- Никаких уведомлений и попапов активности не порождают. Уведомления только явные.
- Создание активности доступно как из чаттера, так и из канала записи.

## 15. Миграция

1. **Чистка followers:** удалить из `mail.followers` всех партнёров, не являющихся внутренними пользователями. Полная чистка, не «оставить и не использовать».
2. **Классификация существующих `mail.message`:**
   - сообщения с внешними получателями и входящие письма → подтип `message`;
   - остальные не-`note` → подтип `comment`;
   - `note` остаются `note`.
3. **Существующие tracking-сообщения не мигрируются.** Подтип `change` начинает применяться только к новым изменениям. Историю не трогаем.
4. **Каналы записей не создаются миграцией.** Создаются лениво по общим правилам (§5.1), при этом подшивают всю историю.
5. При включении режима поиска по содержимому — единоразовое построение полнотекстового индекса на существующей базе (выполнять в окне обслуживания).

## 17. Ключевые технические риски

1. **Объём m2m-связей.** Изменение поля в записи с 50 подписчиками порождает связи со множеством каналов. Схлопывание изменений одного `write` в одно сообщение обязательно; при массовых операциях (импорт, `write` по тысячам записей) нужен батчинг записи связей.
2. **Двусторонняя синхронизация followers ↔ участники канала** склонна к рекурсии. Нужен флаг в контексте, подавляющий обратный вызов.
3. **Синхронизация имени канала** завязана на `display_name`, который у многих моделей вычисляемый. Отлавливать `write` по полям-зависимостям, а не по `display_name`.
4. **Фильтрация `tracking_value` на рендере** по персональной подписке — не забыть про то, что одно сообщение читается разными пользователями с разным результатом; кэш рендера должен быть per-user.
5. **Одноразовые ссылки и почтовые сканеры** — причина требования POST-подтверждения вместо GET.


## 18. Виртуальный чаттер партнёра (планируется)

### 18.1. Идея

Чаттер `res.partner` перестаёт быть лентой сообщений «по самой карточке
контакта» и становится **агрегатором**: показывает сообщения всех записей,
связанных с этим контрагентом — лидов, заказов на продажу и закупку, счетов,
поставок, транспортных заказов, писем MessageBox и т. д.

Агрегация — не копирование. Сообщение по-прежнему существует в единственном
экземпляре и лежит на своей записи-источнике (`model`/`res_id` не
подменяются). Чаттер партнёра — ещё одна **проекция** тех же `mail.message`,
как канал записи в §3.

### 18.2. Три уровня охвата

| Уровень | UI-подпись | Что показывает |
|---|---|---|
| Прямой | **Direct** | только сообщения самой записи `res.partner` |
| Связанный | **Related** | прямой + сообщения всех записей, где этот контакт указан как контрагент |
| Компания | **Company** | связанный уровень для всех контактов организации (`commercial_partner_id`) |

Переключатель — в шапке чаттера партнёра; выбор персистентный per-user
(по умолчанию Related; для физлица без организации Company скрывается).

### 18.3. Что считается «связанной записью»

Связь описывается **явным реестром** «модель → поле-ссылка на партнёра»
(редактируемая таблица в Settings → Technical) с начальным наполнением
(sale.order, purchase.order, account.move, crm.lead, stock.picking,
supply.shipment, supply_contract.contract, transport.order/loading, coa.*,
email.document, ksef.invoice, connect_messagebox.message и др.).
Автоматическое сканирование всех m2o-полей не используется: значительная
часть таких полей означает не контрагента (нашу компанию, лабораторию,
таможенный пост) или дублирует уже учтённое related-зеркалом. Служебные
стороны и второстепенные поля (invoice/shipping-адреса) в дефолт не входят.
Модели со связью через промежуточную запись подключаются хук-методом.

### 18.4. Правила видимости

- Пользователь видит только сообщения записей, которые ему разрешено читать
  (штатные права записи-источника, без sudo). Недоступное не показывается ни
  телом, ни фактом существования.
- Каждое виртуальное сообщение подписано кликабельной ссылкой на
  запись-источник («on SO0025»).
- Виртуальные изменения (`change`) и служебные сообщения в агрегированную
  ленту не попадают; изменения самого партнёра — как раньше, по фильтру §6.
- Агрегация не влияет на счётчики непрочитанного и канал партнёра.

### 18.5. Канал партнёра остаётся реальным

Канал Discuss для `res.partner` создаётся и работает по общим правилам §5 и
показывает исключительно реальные сообщения по самому партнёру; агрегация
живёт только в чаттере. Сообщение из чаттера партнёра публикуется на самом
партнёре — стандартно.

### 18.6. Чего функция не делает

Не переносит сообщения между записями; не даёт писать «в контекст заказа» из
чаттера партнёра; не агрегирует активности, вложения, followers и подписки на
поля; не гасит уведомления чужих записей; не строит рекурсивную агрегацию
глубже прямой связи.

### 18.7. Реализация

Хранилище — обычный SQL VIEW из реестра (решение 2026-08-18); замер
производительности на прод-копии, эскалация к материализованной таблице
только при страницах дороже ~300 мс. Технический дизайн —
`docs/design-virtual-chatter.md`.

## Поправки
Первое — mail.channel.guest.link. Модель называется «ссылка» и содержит поля именно ссылки: token, is_link_consumed, session_token, session_expiry, last_seen. Когда придёт Telegram, участник-клиент будет тем же по смыслу (внешний контакт с доступом к каналу), но с chat_id вместо токена. Это не повод строить абстракцию заранее — это повод назвать модель mail.channel.external.participant и вынести специфику ссылки в отдельные поля. Стоит ноль сейчас и избавляет от переименования модели с миграцией потом.

Второе — правила доставки в кроне. Часовой дайджест в §9.6 написан как глобальное правило системы. Для Telegram он бессмысленный. Достаточно, чтобы условие крона смотрело на транспорт участника, а не выбирало всех внешних подряд.

- Синтетические activity-сообщения (§13): create/перенос/переназначение/отмена

  шаблон, feedback, вложения); автор — актор, для крона OdooBot.

- Обратная проекция §11.2: сообщение из канала записи постится на саму запись

### Фаза 2 — подписка на поля и личный канал Changes (2026-08-18, коммиты 205f0f120..HEAD)

Реализует §4.3, §8 и кнопку Changes из §11.1. Модуль `streams` 15.0.1.2.0.

**Сервер:**

- Доступные поля считаются `fields_get` от лица пользователя (поля с `groups=`
  отсекает само ядро), минус служебные (`message_*`, `activity_*`, `write_*`,
  `create_*`, `rating_*`, `website_message_*`, `access_*`, `display_name`).
- Личный канал Changes (§8.3): `mail.channel._streams_get_changes_channel`,
  ленивое создание при первой подписке, единственный участник — владелец,
  частичный UNIQUE `(channel_kind, owner_user_id)`.
- Маршрутизация (§8.2): в `mail.message.create` change-сообщение (то, у
  которого есть `tracking_value_ids`) линкуется с личными каналами тех
  подписчиков, чьи поля пересеклись с изменёнными. Персональных копий нет,

- Лента `mail.channel.streams_changes_feed(limit, before_id)` (§8.3): элементы

  «поле: было → стало» только по подписанным и доступным полям; записи без
  доступа скрываются ретроактивно (§8.4), привязка в БД сохраняется.
- Счётчик непрочитанного канала Changes считает ЗАПИСИ (§8.3) и учитывает
  права: `_compute_message_unread` разветвлён на канал записи и личный канал.
- Свой bus-тип `streams.changes/updated` владельцу канала (без тела
  сообщения).

**UI:**
- Кнопка **Changes** в чаттере (§11.1) открывает визард

- Личный канал — в собственной категории сайдбара **CHANGES** над MESSAGES

- Лента — OWL-компонент `StreamsChangesFeed` вместо ThreadView (ядровый

  вычитывать сообщения впустую). Имя записи кликабельно, прочитанность — по

  обновление — по `streams.changes/updated`.

**Тесты:** +10 сценариев (`tests/test_streams_changes.py`), всего 33 зелёных.

**Отступления Фазы 2 (зафиксированы):**
1. **Список полей сужен**: помимо служебных имён отброшены нехранимые поля без
   трекинга — ядровый `_mail_track` читает колонку, так что изменение по ним
   не возникает в принципе, а диалог они только раздувают.
2. **Диалог — `many2many_tags`, а не чекбоксы**: у `res.partner` под две сотни
   полей, чекбоксами это нечитаемо; поиск по тегам решает ту же задачу дешевле.
3. **Личный канал получил свою категорию сайдбара**, а не пункт над Messages:
   сайдбар Discuss рисует только категории, а отдельный пункт потребовал бы
   форка шаблона сайдбара.
4. **По шине идёт свой тип `streams.changes/updated` без тела сообщения**, а не
   `mail.channel/new_message`: проверять доступ к записи на каждом изменении
   дороже, чем дать клиенту перезапросить ленту, которая права уже учитывает.
   Счётчик клиент берёт из самой ленты (`serverMessageUnreadCounter`).
5. **Счётчик Changes считается в Python, а не одним SQL**: `COUNT(DISTINCT)` не
   умеет `ir.rule`, а §8.4 требует, чтобы потеря доступа гасила и счётчик.

### Фаза 4 — гостевой доступ клиентов (2026-08-18, коммиты 7bd490c7d..HEAD)

Реализует §4.4 (с поправкой), §9 целиком, §10 в части «внешний контакт
получает письмо только при явной отправке или дайджесте», строки §14 про
гостя и пятый триггер §5.1. Модуль `streams` 15.0.1.4.0.
Дизайн-контракт — `docs/design-phase4.md`, включая блок «Решения по
развилкам (2026-08-18)».

**Сервер:**
- Модель `mail.channel.external.participant` (§4.4 с поправкой): канал,
  контакт, `transport='link'`, токен ссылки и токен сессии (оба
  `groups='base.group_system'`), `history_from`, `is_link_consumed`,
  `active`, `last_seen`, `last_digest_sent`, `anchor_message_id`,
  `invited_by_id`. Три частичных UNIQUE в `init()`: по токену, по сессии и
  по `(channel_id, partner_id) WHERE active` — повторное приглашение
  обновляет ту же строку, отозванные остаются историей. Внешний участник
  сознательно **не** `mail.channel.partner` и **не** `mail.guest`: строка
  участника канала уехала бы в followers через зеркало §5.3, а ядровые
  механики канала (channel_info, unread, seen, шина) остаются нетронутыми.
- Секреты — `secrets.token_urlsafe(32)`, сверка `consteq`. Отдельного
  rate-limiter'а нет (в ядре его тоже нет и он непотокобезопасен); каждый
  промах логируется `warning` с IP.
- Кука сессии `sgsid` = `"<id>|<session_token>"`, `httponly`,
  `SameSite=Lax`, `secure` на https, `path=/streams`, срок = настройка.
  `Lax` заодно закрывает CSRF для json-маршрутов.
- Домен видимости гостя — единственное место, где описано «что видит
  клиент»: `mail.message._streams_guest_message_domain`. Он точно зеркалит
  `_streams_classify_vals` (гостю отдаётся ровно `comment` и `message`) и
  сверяется с классификатором обязательным тестом на матрице
  подтип × message_type.
- Публичный контроллер `/streams/guest/*` (свой, не ядровые `/mail/*`):
  GET по ссылке рисует подтверждение и токен **не** гасит (антифишинг-
  сканеры), POST под ядровым CSRF жжёт ссылку и выдаёт куку, дальше —
  лента/отправка/правка/удаление/реакции/загрузка и выдача вложений.
  Все ORM-операции под `sudo` внутри узких методов модели; ни один параметр
  запроса не попадает в `browse()` без проверки принадлежности каналу.
  Коды: 404 на неизвестный токен и чужое вложение, 410 Gone на отозванный
  доступ, протухшую сессию и архивированный канал.
- Тела сообщений переписываются на выдаче: `/web/image|content/<id>`
  вложений видимого сообщения → `/streams/guest/attachment/<id>`, остальные
  бэкенд-ссылки вырезаются. Токен вложения в URL не светится.
- Приглашение — визард `streams.guest.invite.wizard` (§9.2): несколько
  контактов, у каждого своя ссылка, `Show history from`, галочка письма,
  предупреждение о видимости, список уже выданных доступов с `Revoke`.
  Ссылки показываются с `CopyClipboardChar` для ручной передачи.
- Якорь треда (§9.7): служебное сообщение `message_type='notification'` +
  `mail.mt_comment`. По классификатору это «прочее» — канал не заводит, на
  unread не влияет, гостю не видно; при этом подтип не internal, поэтому
  ответ клиента ядро постит нормальным `email`/`mt_comment`. Каждое письмо
  гостю несёт `References`/`In-Reply-To` якоря; при пустом `reply_to`
  (не настроен catchall) пишется `warning` и предупреждение в визарде.
- Дайджест (§9.6): часовой крон `ir_cron_streams_guest_digest`, кандидаты
  отбираются по транспорту участника (`transport='link'`), отсутствие — по
  `last_seen` старше `streams.guest_presence_timeout` (120 с), окно
  сообщений — за весь период; собственные сообщения гостя не считаются.
  Письмо идёт мимо `_notify_thread` (`mail.template.send_mail` по модели
  участника), содержимого переписки в нём нет. Исключение по одному
  участнику не роняет крон.
- Настройки (§14): срок сессии, интервал поллинга, окно правки, порог
  отсутствия, лимит загрузки, интервал дайджеста (пишется в сам крон).

**UI:**
- Кнопка **Invite customer** в чаттере записи и в шапке канала записи.
- Публичная страница — самодостаточный QWeb без website, без OWL, без
  `web.assets_*` и без `__session_info__`; `guest.css`/`guest.js` отдаются
  обычной статикой. Поллинг раз в 10 с с паузой на скрытой вкладке (это и
  есть heartbeat присутствия §9.5), backoff при сетевых ошибках, остановка
  навсегда на `{'error': 'gone'}`, кнопки Edit/Delete гаснут по таймеру
  локально (сервер перепроверяет).

**Тесты:** +22 сценария (`tests/test_streams_guest.py`), всего 70 зелёных.

**Отступления и решения Фазы 4 (зафиксированы):**
1. **Ротация ссылки — только сожжённой** (`is_link_consumed=True`);
   несожжённая повторяется в дайджесте как есть, иначе ротация убивала бы
   ссылку в неоткрытом письме-приглашении. Кука-сессия при ротации не
   трогается: ротируется ссылка, а не сессия.
2. **Кнопка Invite customer и в чаттере, и в канале**; приглашение из
   чаттера создаёт канал (пятый триггер §5.1). Пункт Б1 дизайна про
   «только в канале» отменён решением пользователя.
3. **Гость видит всех участников канала**: сотрудников — ФИО как есть,
   других внешних — с пометкой `external`.
4. **Удаление гостем — переподтипливание в `mail.mt_note`** с префиксом
   «Deleted by the customer:» перед исходным телом, а не опустошение тела
   (Р7 дизайна). Гость сообщение больше не видит (note не входит в его
   домен), сотрудники видят содержимое в потоке Notes — след и аудит
   сохраняются без новых сущностей; вложения выпадают из гостевой выдачи
   вместе с сообщением. Правка гостем — по-прежнему ядровый
   `_update_content` (гейт снят контекстом `streams_guest_edit`).
5. **Порог отсутствия — 120 с**, настройка `streams.guest_presence_timeout`.
6. **Ответ клиента подписывает пригласившего** (`invited_by_id`), если тот
   ещё не подписан: и через страницу, и по email. Точка одна —
   `mail.thread._streams_handle_posted_message` на потоке `message` с
   автором-участником канала; неактивный или внешний `invited_by` молча
   пропускается с `warning`.
7. **Гейты гостя живут в модели, а не в контроллере** (отступление от
   раскладки А4/А5 дизайна): контроллер занимается HTTP и сериализацией,
   «что гостю можно» описано в одном месте и покрыто юнит-тестами без
   HttpCase.
8. **Реакции пишутся напрямую в `mail.message.reaction`**, а не через
   ядровый `_message_add_reaction`: тот берёт партнёра из `env.user`, а под
   `sudo` это OdooBot. Партнёр у гостя настоящий, поэтому его реакция

   протекал в `search` — гость видел отозванные доступы. Найдено живым

**Ключевые замены:**

  партнёрам (ACL сохранён); правки/реакции гостя — `mail.record/insert`.
